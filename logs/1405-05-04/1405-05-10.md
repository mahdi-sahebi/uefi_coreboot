| # | Issue | Root Cause | Evidence | Fix |
|---|-------|-----------|----------|-----|
| **1** | **UART not working** | `bootblock_mainboard_early_init()` in `bootblock.c` never calls `aspeed_enable_uart_pin()`. It only calls `aspeed_enable_serial()`, which sets the SuperIO logical-device I/O base/enable bit, but **does not route the physical TX/RX pins to the UART function** via the AST2600's SCU multi-function pin-mux registers. | `early_serial.c`: `aspeed_enable_serial()` does enter-conf → set device → set iobase → enable → exit-conf — nothing more. `early_config.c` separately defines `aspeed_enable_uart_pin()`, which sets `MUL_FUNC_PIN_CTL2_REG` bits `UART1_TXD1_EN_BIT`/`UART1_RXD1_EN_BIT` (for SUART1) — this function is **never called anywhere** in `bootblock.c`, `romstage.c`, or `ramstage.c`. Without it, the pins likely remain in their reset/alt function (not UART), so no signal reaches the physical pins even though the SuperIO logical device thinks it's "enabled." | Add, right after the existing `aspeed_enable_serial(...)` call in `bootblock.c`:<br>`aspeed_enable_uart_pin(ast_serial_dev);` |
| **2** | **SOL empty in BMC dashboard (but stock BIOS has SOL output)** | Direct consequence of #1. AST2600 SoL works by the BMC's SoL engine listening to the AST2600's own physical UART pins (SUART1/2) exactly as your comment states ("SUART1 debug header, SUART2 SOL"). If the pins are never muxed to UART function, the AST2600 UART hardware itself never receives/transmits real serial data on the physical lines, so the BMC-side SoL engine (which taps the same physical UART, not the coreboot console buffer) sees nothing — even though coreboot's own `CONFIG_CONSOLE_SERIAL`/CBMEM console is otherwise configured correctly. | Same root cause as #1 — stock ASRock BIOS almost certainly performs pin-mux as part of its SIO init. | Same fix as #1. Once pins are muxed, verify separately whether SUART2 (the one wired to BMC SOL, per your bootblock comment) also needs its own `aspeed_enable_uart_pin()`/decode-window enable — currently only SUART1 (debug header) is enabled at all; **SUART2 (SOL) is never initialized in bootblock.c at all** — only the LPC decode ranges (`LPC_IOD_COMB_RANGE`) are opened, but no `aspeed_enable_serial()`/`aspeed_enable_uart_pin()` call exists for the SUART2 logical device. This is a second, independent gap for SOL specifically. |
| **3** | **Hang/crash in `FaultTolerantWritePei`** | Architectural mismatch between how NV-storage location info is *published* vs *consumed*: `SmmStorePei` (your PEIM) computes the correct flash NV/FTW-working/FTW-spare addresses from coreboot's SMMSTORE CBMEM table and publishes them **only as a GUID HOB** (`gVariableFlashInfoHobGuid`). But `DasharoPayloadPkg.dsc` binds `VariableFlashInfoLib` to `MdeModulePkg/Library/BaseVariableFlashInfoLib` — the **static-PCD-only** implementation. Since `PcdFlashNvStorageVariableBase/FtwWorkingBase/FtwSpareBase` (and matching `*Size` PCDs) are all hardcoded to `0` in the DSC and never overridden anywhere, `GetVariableFlashFtwWorkingInfo()`/`GetVariableFlashFtwSpareInfo()` inside `FaultTolerantWritePei.c` return `WorkSpaceAddress = 0` and `SpareAreaAddress = 0`. The `ASSERT((WorkSpaceAddress != 0) && (SpareAreaAddress != 0))` only fires in debug/assert-enabled builds; in a release-style build it's a no-op, and execution falls through into `IsValidWorkSpace()` (which will legitimately fail against a zeroed/garbage header), which routes into the **backward-scanning search loop**:<br>`WorkSpaceInSpareArea = SpareAreaAddress + SpareAreaLength - WorkSpaceLength;`<br>`while (WorkSpaceInSpareArea >= SpareAreaAddress) { ...; WorkSpaceInSpareArea -= sizeof(EFI_GUID); }`<br>With `SpareAreaAddress = 0`, the loop condition `WorkSpaceInSpareArea >= 0` is **always true for any unsigned value** — so it either underflows through the entire 64-bit address space dereferencing `CompareGuid()` against unmapped memory (crash) or spins effectively forever (hang) until it wraps and coincidentally matches or faults. | `SmmStorePei.c`: builds `gVariableFlashInfoHobGuid` HOB only, no PCD writes. `DasharoPayloadPkg.dsc` lines 330/633–645: `VariableFlashInfoLib\|...BaseVariableFlashInfoLib...` + all `PcdFlashNvStorage*` PCDs `\|0`. `FaultTolerantWritePei.inf`: `[Depex] TRUE` — no dependency on `gVariableFlashInfoHobGuid`, so even if the lib *did* read HOBs, dispatch order isn't guaranteed either. `FaultTolerantWritePei.c`: confirmed underflow-prone loop as described (this matches the PEIM[2] hang behavior you and I previously identified, just with a corrected/updated root cause now that `CONFIG_SMMSTORE=y` is confirmed — the bug isn't SMMSTORE being off, it's that its output HOB is orphaned). | Two-part fix: **(a)** Switch `VariableFlashInfoLib` in `DasharoPayloadPkg.dsc` to a HOB-consuming implementation (a `PeiVariableFlashInfoLib`-style resolution that reads `gVariableFlashInfoHobGuid` when present, falling back to PCDs otherwise) rather than the pure-PCD `BaseVariableFlashInfoLib`. **(b)** Add `[Depex] gVariableFlashInfoHobGuid` (as a PPI-guid depex, or restructure as a HOB-existence check) to both `FaultTolerantWritePei.inf` and `Variable/Pei/VariablePei.inf` so they cannot dispatch before `SmmStorePei` has run. As defense-in-depth, also patch the loop itself to bound-check for `SpareAreaAddress == 0` / use a bounded `for` decrement instead of an unsigned wraparound comparison. |

### Summary
- **Issues 1 & 2 share one root cause**: missing `aspeed_enable_uart_pin()` call(s) in `bootblock.c` — SUART1 pin-mux is skipped entirely, and SUART2 (SOL) isn't initialized at all in the mainboard code you've shared.
- **Issue 3** is a PEI-phase library/HOB architecture bug: `SmmStorePei` produces flash-location data nobody reads, so `FaultTolerantWritePei` operates on zeroed addresses and falls into an unsigned-underflow scanning loop.
